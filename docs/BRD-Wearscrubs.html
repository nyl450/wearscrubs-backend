1Ringkasan Eksekutif

Wearscrubs adalah platform e-commerce baju operasi (scrubs) untuk dokter, dirancang dari awal sebagai pengganti spreadsheet manual menjadi sistem terintegrasi yang bisa dioperasikan satu admin tanpa pelatihan teknis.

Apa Itu Wearscrubs?

Wearscrubs (wearscrubs.id) adalah toko online yang menjual baju operasi premium untuk dokter dan tenaga medis. Brand ini lahir dari pengamatan bahwa scrubs di pasaran umumnya generik, tidak nyaman, dan dijual tanpa pemahaman kebutuhan dokter. Wearscrubs menjawab itu dengan produk yang dirancang oleh dokter, materi yang lebih nyaman dipakai operasi panjang, dan layanan bordir nama + logo institusi untuk personalisasi.

Status Platform Saat Ini

  • Live penuh di domain utama wearscrubs.id dan www.wearscrubs.id dengan SSL aktif.
  • Bilingual Indonesia dan Inggris, 43 halaman publik, semua sinkron.
  • Dashboard admin matang dengan 15+ modul (Kasir, Manajemen Pesanan, Bordir Workflow, Report, Refund, Exchange, RBAC, dll).
  • Database PostgreSQL via Supabase dengan Row-Level Security aktif di 11 tabel publik.
  • Auto-deploy dari GitHub ke Railway setiap push.

2Profil Bisnis

2.1 Latar Belakang & Tujuan

Wearscrubs dimulai dari masalah konkret: dokter butuh baju operasi yang bagus dan rapi, tapi pengalaman pembelian di pasar tradisional (offline atau marketplace generic) buruk. Bahan kasar, ukuran tidak konsisten, layanan bordir nama dokter atau logo rumah sakit hampir tidak ada, dan tidak ada brand yang benar-benar memahami kebutuhan ini.

Owner Wearscrubs (James) — yang juga membangun seluruh platform ini — menyadari gap ini dari pengalaman istrinya sendiri sebagai dokter. Solusinya: brand scrubs premium yang dirancang dari sudut pandang dokter, dijual lewat platform online yang seluruh operasionalnya bisa dijalankan istri sebagai admin tunggal.

Tujuan utama platform: menggantikan spreadsheet manual + WhatsApp manual + invoice manual menjadi satu dashboard intuitif yang menangani seluruh siklus pesanan dari order masuk sampai paket diterima customer.

2.2 Target Pengguna

SegmenKarakteristikKebutuhan Utama
Dokter individu Dokter umum, spesialis, residen. Order 1-3 set per pembelian. Kenyamanan bahan, ukuran tepat, bordir nama profesional, pengiriman cepat.
Tim / Departemen RS Order bulk (5-30 set) dgn bordir logo institusi. Konsistensi warna seragam, bordir logo presisi, invoice rapi, ongkir terkelola.
Klinik / Praktek mandiri Order recurring (3-10 set per pembelian). Konsistensi stok, opsi custom size, after-sales response cepat.
Mahasiswa kedokteran Order untuk koas / praktek lapangan, biasanya 1-2 set. Harga terjangkau, ukuran lengkap, pengiriman ke kota tujuan koas.

2.3 Nilai yang Ditawarkan

Berbeda dari marketplace generic dan toko scrubs konvensional, Wearscrubs membawa 4 keunggulan inti:

  • Dirancang oleh dokter. Setiap produk dievaluasi dari sisi fit, mobilitas, dan daya serap keringat dari sudut pandang dokter aktif — bukan vendor garmen umum. Badge "Dirancang oleh Dokter" ditampilkan eksplisit di halaman produk.
  • Bordir nama & logo profesional. Layanan bordir nama dokter (dgn pilihan warna benang, posisi dada kiri/kanan) dan bordir logo institusi tersedia di setiap pembelian. Layanan ini umumnya tidak ada di kompetitor.
  • Custom size & custom product. Customer tidak terbatas pada katalog standar — admin dapat membuat order untuk ukuran di luar katalog (4XL, dll) atau bahkan produk yang full-custom (nama, kategori, harga semua manual). Cocok untuk kebutuhan khusus klinik atau RS yang minta spesifikasi unik.
  • Layanan admin responsif. Setiap order dipantau langsung oleh istri sebagai admin, dengan WA notifikasi otomatis di setiap step (konfirmasi bayar, packing, kirim resi, selesai). Tidak ada anonimitas marketplace.

2.4 Filosofi Desain Sistem

Sistem dirancang dengan prinsip "satu admin tanpa pelatihan harus bisa pakai". Konsekuensi desain dari prinsip ini:

  • Bahasa Indonesia di seluruh dashboard. Tidak ada jargon teknis. Label tombol kontekstual ("Kemas Barang", "Input Resi / Kirim", "Tandai Diterima") — bukan generik "Submit" atau "Update Status".
  • Visual gate. Tombol action di-disable + diberi label penjelas ("Review Bordir Dulu", "Bayar Selisih Dulu") kalau ada prasyarat belum dipenuhi. Admin tidak perlu mengingat aturan — sistem yang mengingatkan.
  • Step-by-step. Status pesanan progresif dengan tombol yang muncul sesuai konteks. Tidak ada layar dengan 20 tombol yang membingungkan.
  • Panduan tertanam. Menu "Bantuan" di sidebar berisi panduan in-app untuk setiap modul, plus dokumen PANDUAN-ADMIN.md yang bisa dicetak.

3.3 Alur Sinkronisasi Kode

Workflow git dirancang seminimal mungkin agar siklus edit-deploy cepat:

1. Edit file langsung di repo utama D:\ws\wearscrubs-backend\ menggunakan path absolut.
2. Commit dengan git -C "D:/ws/wearscrubs-backend" add && commit.
3. Push ke origin main. Tidak perlu worktree, tidak perlu ff-merge manual.
4. Railway auto-deploy terpicu otomatis lewat webhook GitHub. Build + restart container ~1-2 menit.
5. Verifikasi dengan refresh wearscrubs.id atau dashboard admin.

Untuk perubahan di file HTML publik yang memakai class Tailwind baru, perlu rebuild CSS dulu:

npx tailwindcss@3 -c tailwind.config.js -i tw.input.css -o public/tw.css --minify

Dashboard admin TIDAK butuh rebuild karena masih pakai Tailwind CDN.

4Modul Website Publik

43 halaman responsif, bilingual ID/EN, mobile-first, SEO komplit. Customer journey: cari produk → pilih varian → atur bordir → checkout → terima konfirmasi WA.

4.1 Beranda (Homepage)

URL: / (ID) dan /index-en.html (EN).

Tujuan: mengarahkan visitor ke kategori produk dalam < 5 detik, sambil membangun trust lewat narrasi brand "dirancang oleh dokter".

Komponen Utama

  • Sticky pill header — navigasi mengambang transparan dengan blur, invert ke white pill saat scroll. Di desktop homepage menggunakan xl:fixed sehingga hero nempel di atas.
  • Hero section — judul utama + CTA "Belanja Sekarang" + thumbnail kategori unggulan.
  • Section kategori — 4 kategori utama (Tops, Pants, Caps, Gown) sebagai entry point.
  • Section "Terlaris" — produk pilihan dengan teaser harga.
  • News teaser — 3 artikel terbaru gaya hidup medis dgn CTA "Lihat Semua" ke news.html.
  • Footer charcoal — rounded-t-[48px] dengan link halaman statis + sosial media.

4.2 Halaman Kategori

8 halaman kategori (4 kategori × 2 bahasa) menampilkan grid produk lengkap dengan filter implisit per kategori.

  • category-tops.html / -en.html — Atasan scrubs lengan pendek & panjang.
  • category-pants.html / -en.html — Celana scrubs.
  • category-caps.html / -en.html — Topi operasi (caps).
  • category-gowns.html / -en.html — Gown operasi.

Setiap halaman dilengkapi JSON-LD BreadcrumbList statis untuk SEO breadcrumb di Google.

4.3 Halaman Detail Produk

URL: product.html?id={id} (ID) dan product-en.html?id={id} (EN).

Halaman ini paling kompleks di sisi publik karena harus menangani:

  • Cascade pilihan varian — warna → variant_type (Lengan Pendek/Panjang) → ukuran (S/M/L/XL/XXL). Setiap perubahan memuat ulang stok riil dari API.
  • Resolusi harga per varian — produk dengan price_by_type menampilkan harga berbeda per pilihan lengan (mis. Pendek Rp 245.000, Panjang Rp 260.000).
  • Pilihan bordir nama — input teks nama, baris ke-2 opsional (jabatan/gelar), warna benang, posisi dada (kiri/kanan), preview harga.
  • Pilihan bordir logo — upload gambar logo (PNG/JPG, max 1.8MB), atau pilih "kirim lewat WA nanti".
  • Stok info live — info ketersediaan stok untuk varian terpilih.
  • Add to cart — payload disimpan di localStorage untuk sinkronisasi cross-page.

Halaman juga mengembed JSON-LD Product dinamis dengan offers/price/availability untuk rich snippet Google.

4.4 Keranjang (Cart)

URL: cart.html / cart-en.html.

  • Render item dari localStorage dengan HTML-escape (anti-XSS).
  • Edit qty per item, hapus item.
  • Subtotal otomatis.
  • CTA "Lanjut Checkout" → checkout.html.

4.5 Checkout 5 Langkah

URL: checkout.html / checkout-en.html.

Customer journey dibagi 5 step linear untuk mengurangi kognitif load dan abandonment:

Step 1 — Data Pelanggan: nama, nomor WhatsApp (validasi format 08xxx / 62xxx, 9-15 digit), alamat lengkap.
Step 2 — Pengiriman: pilih kota tujuan dari dropdown 380+ kota Indonesia. Berat dihitung otomatis (qty / 3 kg). Ongkir di-resolve via CITY_RATES (override per-kota; 100% kota Indonesia di 38 provinsi sudah ber-tarif spesifik dari owner), dengan ZONE_RATES 5-zona sebagai fallback murni. Kurir auto-pilih berdasar zona kota. Rule "Kabupaten ikut induk" untuk kabupaten satelit kota inti.
Step 3 — Metode Pembayaran: Transfer Bank (BCA) atau QRIS. Panel kondisional menampilkan nomor rekening atau gambar QRIS WS sesuai pilihan.
Step 4 — Review & Konfirmasi: ringkasan order, total, ongkir, grand total. Customer cek dulu sebelum submit.
Step 5 — Submit: POST ke /api/orders. Backend validate & insert dalam transaksi atomik. Customer dapat order code, dan instruksi pembayaran (transfer 2x24 jam atau auto-cancel).
Anti-tamper: ongkir di-recompute server-side dari kota + qty (bukan dipercaya dari klien). Diskon dipaksa 0 untuk order publik (hanya admin via Kasir yg bisa pakai diskon).

5.2 Overview Dashboard

Landing setelah login. Menampilkan ringkasan harian/mingguan: total pesanan masuk, "Uang Masuk (Kotor)" hari ini (termasuk ongkir, sebelum refund — beda dengan Net Sales di Report yang sudah dikurangi diskon & refund), jumlah pesanan butuh aksi (menunggu bayar, menunggu kemas, dll), badge notifikasi di sidebar untuk Pre-Order, Refund pending, dan Exchange pending.

Catatan terminologi: label "Total Pendapatan" sebelumnya membingungkan karena beda formula dengan Net Sales di Report. Kini diberi nama eksplisit Uang Masuk (Kotor) dengan subtitle "Termasuk ongkir, sebelum refund · cek Report utk Net Sales".

5.3 Manajemen Produk

  • CRUD produk dengan multi-varian (warna × variant_type × size).
  • Upload foto produk (multi-image per varian, slot 1-5).
  • Kategori: tops / pants / caps / gown (CHECK constraint di DB).
  • price_by_type: harga berbeda per variant_type (mis. Pendek vs Panjang).
  • Soft-delete: is_active = false menyembunyikan dari halaman publik, history pesanan tetap utuh.
  • Atomic upsert: foto di-upload ke Storage sebelum transaksi DB, sehingga gagal di tengah tidak meninggalkan produk parsial.

5.4 Manajemen Stok (Inventory)

Salah satu modul paling matang. Setiap mutasi stok ber-log di tabel stock_movements dengan movement_type spesifik.

Fitur Utama

  • Card view + Grid view — admin pilih layout sesuai preferensi.
  • Inline edit cepat di grid view: klik cell stok → input langsung → save.
  • Modal "Terima Stok" — input stok baru dengan note. Bisa pilih: kondisi normal / reject. Pre-Order eksisting otomatis terpenuhi (FIFO, paid-only) saat receive.
  • Reject to Normal — konversi stok reject jadi normal kalau setelah dicek ulang ternyata oke.
  • Bulk edit dengan threshold grid (set multiple varian sekaligus).
  • Opname mode — penyesuaian stok dengan alasan whitelist (5 alasan: hitung ulang, kerusakan, hilang, ditemukan, lain-lain).
  • Variant History modal — riwayat pergerakan stok + daftar pembeli per varian.
  • Badge "N PO" di card/grid — tanda ada Pre-Order menunggu varian ini.

5.5 Manajemen Pesanan

Modul utama. Setiap pesanan ditampilkan sebagai card dengan informasi pelanggan, item, total, status, dan tombol action kontekstual.

Tab Layout (Redesign Juni 2026)

Tab utama disusun ulang berdasar urgensi, default landing langsung ke yang butuh aksi:

  • Perlu Aksi (default) — sub-tab: Belum Bayar · Minta Logo · Review Bordir · Tunggu PO · Tunggu Custom (predicate scan items unfulfilled per kategori).
  • Proses — order yang sedang berjalan (confirmed/bordir/packed/shipped).
  • Arsip — done + cancelled.
  • Semua — escape hatch tanpa filter.

Helper Scroll & Flash Highlight

Tombol gate amber ("Bayar Selisih Dulu", "Review Bordir Dulu", "Tandai Custom Siap Dulu") membuka modal lalu memanggil scrollToModalAnchor() — menggunakan modal.scrollTo(offsetTop) (bukan scrollIntoView yang gagal di nested scroll Safari/Chrome) + class .flash-highlight CSS pulse 1.5 detik sky cyan untuk menarik mata admin ke section relevan.

Status Pesanan (State Machine)

pending — Order baru masuk, menunggu konfirmasi bayar.
confirmed — Pembayaran dikonfirmasi admin (upload bukti). Stok ter-deduct di sini.
bordir — Khusus order dengan bordir. Menunggu istri review & proses bordir.
packed — Barang dikemas, siap dikirim.
shipped — Resi diinput, paket dalam perjalanan.
done — Paket diterima customer. Siklus selesai.
cancelled — Dibatalkan. Kalau sudah paid, stok di-restore + auto-create refund record.

5.6 Modul Kasir (5 Sumber Order)

Sebelumnya bernama "Input Order WA", dinamakan ulang jadi "Kasir" karena fungsinya sudah jauh melampaui WhatsApp order. Modul ini handle 5 jenis sumber pesanan:

SumberSkenarioTreatment Khusus
websiteOrder dari halaman publik wearscrubs.id.Default, biasanya tidak dibuat manual.
whatsappCustomer order via chat WA, admin input manual.Setelah submit, builder pesan WA otomatis untuk customer.
event_offlineBooth di event medis (konferensi, simposium).Bisa pilih bayar Cash / QRIS / Free.
offlineWalk-in di toko fisik.Sama dengan event_offline.
collaboration_eventKerjasama partner — pembeli bayar ke partner, kita tagih partner dgn consignment 30%.Wajib isi billing_to (nama partner). Diskon 30% dipilih manual.

Fitur Kasir Lanjutan

  • Cascade dropdown produk: warna → variant_type → ukuran, dengan stok info live.
  • Custom Size: opsi "✏️ Custom Size" di dropdown ukuran — input label bebas (mis. 4XL) + harga manual. Off-catalog, skip cek stok.
  • Custom Warna: opsi "✏️ Custom Warna" di dropdown warna — label warna bebas + harga manual.
  • Custom Product: opsi "✨ Custom Product" di dropdown produk paling bawah — semua field manual (nama, kategori, variant, warna, ukuran, harga). Full off-catalog.
  • Pre-Order toggle: muncul otomatis kalau qty > stok. Whole-item PO, stok dialokasi saat barang datang (FIFO, paid-only).
  • Bonus toggle: tandai item sebagai bonus (Rp 0). Stok tetap di-deduct, harga di-nol-kan.
  • Bordir per-item: nama (dgn baris ke-2 opsional), logo (upload PNG/JPG atau placeholder "kirim via WA"), warna benang, posisi dada kiri/kanan.
  • Diskon: pilihan 0% / 5% / Consignment 30% (validasi server-side).
  • Result panel adaptif: setelah submit, panel hasil menampilkan instruksi bayar yang sesuai sumber + metode (QRIS image / BCA-Mandiri / Cash / Collab note).

5.7 Bordir — Workflow Lengkap

Salah satu fitur paling kompleks karena melibatkan banyak edge case bisnis: review pre-payment vs post-payment, request tambah bordir setelah bayar, validasi posisi, tolak total order, dll.

Aturan Bisnis Lock

  • 1 baju maks: 1 nama + 1 logo. Tidak ada 2 logo per baju.
  • Bordir hanya untuk Atasan (tops) & Gown — celana/cap pill bordir disabled di Kasir.
  • Default harga: nama Rp 20.000, logo Rp 30.000. Admin bisa override per-order.
  • Posisi: kiri / kanan dada. Kalau both nama+logo aktif di 1 baju → posisi wajib beda.
  • Baris ke-2 nama opsional — mis. jabatan/gelar di baris bawah (Sp.PD, M.Kes).

Visual Gate Hard-Block

Untuk order non-website dengan bordir, tombol "Konfirmasi Pembayaran" di-block dengan label amber "🔍 Review Bordir Dulu". Klik tombol → scroll ke section Review Bordir. Istri WAJIB klik Setujui/Tolak dulu sebelum konfirmasi bayar.

Tolak Bordir = Cancel Total Order

Sesuai keputusan owner: tidak ada flow "lanjut tanpa bordir" di order yang sama. Kalau bordir bermasalah, customer perlu order baru. Tombol "Tolak & Batalkan Pesanan" → modal alasan (3 quick-pick: "Logo terlalu rumit" / "Nama terlalu panjang" / "Kualitas logo") → cancel endpoint dipanggil dengan set_bordir_status='rejected' untuk audit trail.

Tambah Bordir Post-Payment

Customer berubah pikiran setelah bayar — minta tambah bordir. Tombol "+ Tambah Bordir" muncul kondisional (payment paid, status bukan shipped/done/cancelled, tidak ada outstanding, ada item yang belum punya bordir). Flow:

  1. Admin pilih item belum bordir → isi detail (nama+baris2+text+warna+posisi+harga, atau logo).
  2. Backend update items, rebuild embroidery_details, reset bordir_status='pending'.
  3. Auto-open template WA tagihan: "Selisih Rp X, transfer BCA/Mandiri".
  4. Banner amber di detail: "💰 Outstanding Selisih Bordir Rp X".
  5. Admin konfirmasi bayar selisih → upload bukti → set additional_paid_at.
  6. Section Review Bordir aktif → istri Setujui / Tolak.

5.8 Edit & Split Pesanan

Edit Pesanan

Tombol pensil di header modal detail order. Auto-hidden untuk staff non-admin atau order shipped/done/cancelled. Field editable: nama, HP, alamat, kota, kurir, berat, ongkir, metode bayar, sumber, billing_to (kondisional collab), notes.

Total otomatis ter-recompute kalau ongkir berubah (formula: total_baru = total_lama - ongkir_lama + ongkir_baru, deterministik, tidak re-derive dari items supaya anti-drift).

Sengaja TIDAK editable: items & diskon. Mengubah ini = risk drift sumber kebenaran. Kalau salah → cancel + recreate.

Split Order

Use case: event campur — sebagian customer ambil di booth, sebagian minta dikirim. Tombol "Pisah Pesanan" muncul kondisional (admin + status editable + ≥2 items).

  • Original RETAINED (bukan cancel) — items subset di-move via UPDATE order_id.
  • Child = order baru dengan order_code baru, copy customer + payment context.
  • Diskon dibagi proporsional ke subtotal items. Rounding diserap original supaya sum tetap = diskon asli.
  • Bordir flags recompute per pihak. Embroidery details share ke kedua sisi tapi filter per item_label.
  • Audit notes append [Dipisah dari/jadi #X] di kedua sisi.

5.9 Pickup Auto-Skip

Konstanta server: PICKUP_COURIER = 'Diambil di event / walkin'. Kalau kurir = pickup courier, sistem auto-skip step Kemas + Kirim:

  • Confirm-payment + no bordir → status langsung done.
  • Confirm-payment + bordir → status bordir dulu (perlu proses bordir).
  • Bordir-done dgn pickup → langsung done.
  • Defensive: kalau order lama di status confirmed dgn pickup courier, tombol "Kemas Barang" diganti "Tandai Diambil & Selesai" yang jump ke done.

5.10 Refund & Cancel

Hanya admin yang bisa cancel order. Behavior tergantung status pembayaran:

  • Pre-payment cancel: status → cancelled, tidak ada restore stok (belum keluar), tidak ada refund (uang belum masuk).
  • Post-payment cancel: status → cancelled, stok di-restore (per item, kecuali custom yang tidak punya inventory), auto-create refund record dengan status pending. Admin follow up transfer manual lalu mark transferred dengan bukti.
  • Cancel max sampai packed. Order yang sudah shipped tidak bisa cancel (harus pakai flow exchange/refund post-receive).

5.11 Exchange (Tukar Size)

Customer terima paket, ternyata size tidak pas. Flow:

  1. Customer hubungi admin via WA, kirim foto label.
  2. Admin buat exchange di modul Pesanan: pilih item, size tujuan, alasan (size_mismatch / defect), shipping fee.
  3. Exchange created dengan status pending. Custom items (custom_product / custom_size) tidak bisa tukar — opsi disabled + backend reject 400.
  4. Approve → stok size baru di-reserve (exchange_replacement_out), customer kirim balik barang asli.
  5. Admin terima balik → tandai return_received → stok size asli di-restore (exchange_return_in). Status → completed.

5.12 Menu Pre-Order

Sidebar menu "Pre-Order" dengan badge counter. List semua line item yang masih menunggu (PO katalog + Custom Size + Custom Product), diurutkan FIFO (tertua dulu). Setiap row menampilkan:

  • Badge type: 📦 PO KATALOG / ✂️ CUSTOM / ✨ CUSTOM PRODUCT.
  • Badge status bayar: LUNAS / BELUM BAYAR.
  • Stok varian saat ini (untuk PO katalog).
  • Umur hari (warning >7 hari orange, >14 hari red).
  • Tombol "Tandai Siap" (manual fulfill untuk custom; otomatis untuk PO katalog saat receive stok).

5.13 Modul Report

3 tab analytics dengan filter tanggal (mobile-friendly stack vertikal dengan -webkit-appearance:none untuk fix iOS Safari date picker overflow):

  • Sales: grafik omzet harian + breakdown per metode bayar.
  • Sales Type: breakdown per sumber order (website, whatsapp, event, offline, collab).
  • Items: ranking produk berdasar qty terjual + total omzet. Custom items tidak masuk report ini by design (tidak ada di tabel products).

Hanya paid + non-cancelled orders yg dihitung. Bonus items excluded dari omzet.

5.14 Manajemen User

Hanya admin yang bisa akses. CRUD user dengan role assignment + per-menu permission untuk role staff. Password di-hash bcrypt. PATCH user di-batasi: tidak boleh self-lockout (deactivate atau demote diri sendiri).

5.15 Panduan In-App

Menu "Bantuan" di sidebar, accessible untuk semua role. Berisi panduan tutorial per modul dengan tombol "Cetak / PDF" untuk dibawa offline. Tersedia juga sebagai file PANDUAN-ADMIN.md di repo.

7Keamanan & Privasi

Multi-layer defense: autentikasi, otorisasi, anti-tamper, RLS database, escape policy XSS, storage privat.

7.1 Autentikasi (JWT)

  • Password di-hash dengan bcryptjs (cost 10).
  • Login endpoint diparameterisasi penuh (tidak ada SQL injection), error message generik ("Username atau password salah") supaya tidak leak info user exists.
  • Rate limit 5 attempts per 15 menit per IP via loginLimiter.
  • JWT secret di Railway env (JWT_SECRET, wajib di production, fatal kalau missing).
  • Token expiry 8 jam, disimpan di localStorage admin.
  • Seed admin production wajib pakai env ADMIN_INITIAL_PASSWORD minimal 12 karakter.

7.2 Otorisasi (RBAC Per-Menu)

  • 3 role: admin / manager / staff.
  • requireMenu('menu','action') middleware di setiap endpoint memvalidasi token + permission.
  • Staff allowed_menus JSON memetakan menu → permission (view/edit). Per-menu granular.
  • Cancel order dan refund requires requireAuth(['admin']) — admin only.
  • Staff bisa setujui bordir tapi tidak bisa tolak (tolak = cancel = admin only).

7.3 Anti-Tamper (Admin-Only Flags)

Flag berikut di payload POST /api/orders di-gate behind isAdmin:

  • is_bonus — kalau true, produk gratis. Public caller mengirim ini diabaikan.
  • is_custom_size — skip stok check, harga manual. Admin only.
  • is_custom_product — full off-catalog, semua field manual. Admin only.
  • is_po — pre-order, skip stok. Admin only.
  • discount_percent — public dipaksa 0%, hanya admin yang bisa kirim 5% atau 30%.
  • order_source — public dipaksa website, hanya admin yang bisa kirim whatsapp/event/offline/collab.
  • shipping_cost — public di-recompute server-side dari kota+qty. Hanya admin yang trusted untuk set manual.
  • bordir_nama_price / bordir_logo_price — public dipaksa 20rb/30rb default, hanya admin bisa override.

7.4 Row Level Security (Supabase)

11 tabel publik di-ENABLE RLS tanpa policy. Role postgres yang dipakai backend punya rolbypassrls=true, jadi backend tetap jalan normal. Tapi anon key (yg dulu pernah ter-share di chat) ter-block:

  • Read via anon → return [] (kosong).
  • INSERT via anon → error 42501 RLS violation.

Sebelumnya terbukti bocor: anon key bisa baca tabel products & users (username admin). Sekarang tertutup.

7.5 Escape Policy (XSS Defense)

CSP Helmet sengaja dimatikan untuk fleksibilitas styling — jadi escape data customer adalah pertahanan XSS utama. 3 helper escape digunakan konsisten:

  • esc(str) — body innerHTML (escape & < > " ').
  • escAttr(str) — atribut single-quote inline onclick.
  • escEx(str) — modul Exchange (legacy).

Setiap render data customer ke innerHTML WAJIB di-escape. Audit pass 8 Juni menutup 7 area yang sebelumnya un-escaped.

7.6 Storage Privat (Signed URL)

  • Bucket public wearscrubs: foto produk + logo brand. URL public OK.
  • Bucket privat wearscrubs-orders: bukti pembayaran, bukti packing, bukti bordir, bukti refund. Akses hanya via signed URL dengan expiry 1 jam yang di-generate server saat admin login + buka detail order.
  • Endpoint GET /api/orders/:id/photos requires auth — sebelumnya anon bisa enumerasi bukti, sekarang tertutup.

7.7 CORS

  • ALLOWED_ORIGINS env variable di Railway, bukan wildcard *.
  • Hanya domain wearscrubs.id + www + railway preview yg diizinkan.

7.8 Audit Trail

Setiap mutasi penting tercatat:

  • Stock movements — semua mutasi stok ber-type + admin_user + timestamp.
  • Order photos — setiap step (confirm-payment, bordir, pack, ship, refund, done) tercatat dengan performed_by. Step "done" pun bikin audit row meski foto NULL.
  • Bordir status changes — bordir_status + bordir_reject_reason.
  • Cancel — cancelled_by + cancel_reason.
